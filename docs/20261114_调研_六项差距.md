## 1. 登录：WebView

### 阅读怎么做

- 【源码】两条登录路径按 `loginUi` 是否为空二选一（`ui/login/SourceLoginActivity.kt:26-34`）：
  - **表单路径**：`loginUi` 非空 → 5 种控件（text/password/button/toggle/select）→ 控件 action 执行
    `loginUrl + action` 的 JS → 成功则 AES 加密存 `loginInfo`。
  - **WebView 路径**：`loginUi` 为空 → `loginUrl` **当 URL** 加载进 WebView →
    `onPageFinished` 时 `CookieManager.getCookie(url)` 抓 cookie → 存 `CookieStore`。
    **该路径不执行 `loginCheckJs`、不写 `loginInfo`**。
- 【源码】登录编排 816 行住在 UI 层（`SourceLoginDialog.kt`），无法从 UI 剥离（分层问题）。
- 【联网】官方文档镜像描述同一链路：WebView 登录 → Cookie 持久化 → 后续请求自动携带
  （[Legado 书源规则说明](https://mgz0227.github.io/The-tutorial-of-Legado/Rule/source.html)）。

### RSL 现状（【实测】代码）

- `login.type` 枚举含 `qr`（`analyze/mod.rs:2339`），但**没有 `webview` 交互式登录的契约与执行路径**。
- `WebViewPort` 端口已存在（`ports.rs:59`），但只有**单次渲染**语义：
  `render(WebViewRequest) -> WebViewResult{body, sniffed}`——为 `engine: webview` 抓页面服务，
  不是"打开交互式会话让用户操作"。
- `E_CHALLENGE`（人机验证，宿主介入）已定义（`ERRORS.md §4.7`）。
- 结论：**端口能力和错误码都在，缺的是"交互式登录会话"的协议契约**。

### 业界参考（【联网】）

- **Tachiyomi/Mihon 的 WebViewInterceptor 模式**（[扩展库 Dokka 文档](https://mokc.github.io/docs/)）：
  OkHttp 拦截器检测 challenge 响应（HTTP 403/503 + `cf-mitigated` 头）→ 交给内嵌 WebView 执行
  JS challenge（含 Turnstile）→ 回捕 `cf_clearance` cookie + WebView UA → 注回 OkHttp 客户端
  （共享 CookieJar）。同一模式复用于扩展登录（WebViewActivity 加载站点、嗅探认证 cookie）。
- **头号失败模式是 UA 不一致**：WebView 的 UA 与 HTTP 客户端 UA 不匹配时 Cloudflare 拒收 cookie
  （[社区排障指南](https://tachiyomitips.com/tachiyomi-failed-to-bypass-cloudflare)）——
  跨客户端"借 cookie"必须保证 UA 一致，这是被社区反复踩过的坑。

### 差距与可选设计空间（不决策）

| 选项 | 形态 | 代价/风险 |
|---|---|---|
| A. `login.type=webview` 契约化 | 声明入口 URL + 成功判定（cookie/URL 模式），执行归宿主 | 需要新增"交互会话"端口语义 |
| B. 端口扩展 `LoginSessionPort` | `begin(url) → poll() → result{cookies, ua}` 三方法，同步轮询模型 | 内核保持同步可维持；宿主实现交互 UI |
| C. UA 一致性写进契约 | WebView 回捕的 cookie 必须与 `http.headers` UA 同源才有效 | 直接吸收 Tachiyomi 头号教训 |
| D. 维持现状（宿主全权处理） | 内核只消费 CookieStore | 与"UI 不进标准"立场一致，但 `qr` 枚举悬空 |

## 2. 失效自动重登

### 阅读怎么做

- 【源码】**没有自动重登机制**——登录只能手动触发（22 处 `startActivity<SourceLoginActivity>`、
  JS `java.open("login")`、`java.login()`）。`KERNEL-COMPARE.md §279`。
- 【源码 + 联网】一个**文档/源码分歧点**：官方文档称 `loginCheckJs` "检测登录是否失效，失效时自动弹出
  登录页"（[规则说明](https://mgz0227.github.io/The-tutorial-of-Legado/Rule/source.html)），
  但源码事实是 `loginCheckJs` 实为**响应改写器**（`evalJS(checkJs, result)`，返回码 500 时重抛原异常），
  五阶段全部执行但与重登无关（`WebBook.kt:71-95,147-171,…`）。社区排错文章也把登录机制变化列为
  书源失效主因之一（[书源规则排错指南](https://blog.csdn.net/gitblog_00160/article/details/153229813)）。
- 【联网】社区的"自动修复"现状：**没有一键自动修复方案**。批量连通性检测靠第三方工具
  （[LS-Toolkit：清洗/校验/去重/质量评分/连通性检查](https://github.com/aminaqvq/legado-source-toolkit)）
  或自制 Python 脚本，修复靠人 + 社区源合集月更。

### RSL 现状（【实测】代码）

- `ensure_login`：`login.check`（TTL 默认 300s 缓存）→ 失败即 `E_LOGIN_REQUIRED`
  （`login.rs:18-62`），**语义上就是"停机并请宿主弹登录 UI"**——与阅读同构：**没有自动重登循环**。
- `StageResult` 已有 `partial`/`E_CANCELLED`；请求级 `retry`（times/backoff）已有——
  但登录重试与请求重试是两回事，未打通。
- A5 取消令牌（CancelToken）已就位，可约束任何自动循环。

### 业界参考（【联网】）

- Tachiyomi 的拦截器模式是**事实上的自动路径**：challenge/失效响应被拦截 → WebView 处理 →
  回捕 → **自动重放原请求**（用户无感或一次点击）。见 §1 的 interceptor 引文。
- 批量侧：LS-Toolkit 的"连通性检查 → 剔除失效"是检测自动化；修复仍人工。

### 差距与可选设计空间（不决策）

| 选项 | 形态 | 关键风险 |
|---|---|---|
| A. 契约化自动重登 | `login.relogin: { max: 1, on: [E_LOGIN_REQUIRED] }`——check 失败 → 自动执行 `login.steps`/`submit` → 重放原阶段一次 | 表单凭据需已存（secret 字段持久化语义）；循环上限必须硬编码（防打站点） |
| B. 宿主驱动重登 | 内核保持"报 `E_LOGIN_REQUIRED` 即停"，宿主完成登录后**重入 run_stage** | 零契约改动；跨端宿主各自实现，行为不一致 |
| C. 分层混合 | 内核做"重登后重放一次"的机械部分；交互步骤（验证码）仍 `E_CHALLENGE` 抛给宿主 | 折中；需定义"机械重登"不含交互的判定 |
| D. 维持现状（显式不自动） | 与阅读一致，靠 `E_LOGIN_REQUIRED` 文档化 | 兼容立场最强，体验最弱 |

## 3. JS 脚本

### 阅读怎么做

- 【源码】Rhino 引擎；宿主面 `JsExtensions` **120 个 fun**（49 个 `@JavascriptInterface`）+
  `JsEncodeUtils` 30 + `RegexJsExtensions` 6；沙箱 = 类黑名单（RhinoClassShutter 46-179）+
  只读包装 + 禁隐式全局。93 处注入/13 文件，`java` 在 7 个上下文是不同对象。
- 【联网】`jsLib` 远程库 + `java.cacheFile(url, saveTime)` 缓存是常见组合
  （[Autsunset/legado-vox](https://github.com/Autsunset/legado-vox)、官方频道更新记录）。

### RSL 现状（【实测】代码）

- 两档隔离：pure（删 Date/fetch/setTimeout，无 IO 无时间无随机）+ ctx（十接口白名单桥）。
- `ScriptEngine` 端口：Boa（默认，全平台一致）+ QuickJS（`engine-quickjs`，基准 2.0–3.4×，
  双引擎 55/55 等价）。libSteps 计量 + 中断 handler + `NoHost` 兜底（永不 panic）。
- ctx 能力面：var/config/http(get/post)/cache/session/cookie/log/crypto(digest+sym)/now/rand。
- 表达式子语言 `expr:` 编译期类型检查（27 用例原型 + 内核实现）。

### 业界参考（【联网】）

- **QuickJS WASM 沙箱模式**（[sebastianwessel/quickjs](https://github.com/sebastianwessel/quickjs)、
  [运行时选项文档](https://quickjs-sandbox.sebastianwessel.net)、
  [rquickjs worker 沙箱实践](https://daviddalbusco.com/blog/a-self-hostable-wasm-sandbox-for-javascript-workers)）：
  - **能力模型**：guest 无 ambient authority——host 显式注入 fetch/fs/timers，每个都是可拒绝、
    可限定、可包装校验的 capability；
  - **资源限制**：内存上限、超时/中断 handler、栈限制；
  - **业界共识**：JS 层沙箱不可信，外层要有 WASM/进程隔离。
  - RSL 的两档 + 白名单 + 计量与该模型**同构**，且已有 Rust 侧隔离边界。
- 对比阅读的 Rhino：黑名单类加载 + 120 个直通宿主函数——攻击面大得多，但表达力也大得多。

### 差距与可选设计空间（不决策）

| 选项 | 形态 | 说明 |
|---|---|---|
| A. ctx 能力面按需扩权 | `requires.perms: ["net","fs-temp"]` 声明式扩权 + 白名单核对 | 与"能力按需付费"公理一致；每加一个方法都进审计面 |
| B. webJs 桥统一 | WebView 内 JS 与 lib.ctx 共享同一套受控桥 | 现状 webJs 是"页面里跑的自由 JS"，语义未收敛 |
| C. 保持收窄（现状） | `java.*` 永不采纳（GAP-AUDIT §16 已裁决） | 表达力弱是**故意的**；真实站点需求用 `ctx.crypto/http` 覆盖（七猫 L3 已证） |
| D. 双引擎默认化 | CLI/绑定默认 QuickJS（基准 2–3.4×） | wasm 端维持 Boa（V2-D2）；需全面回归 |

## 4. 规则编辑器

### 阅读怎么做

- 【实测/联网】App 内**文本框 + 调试日志**（搜索/详情/目录调试），无结构化编辑器；
  2026 年的系统性教程仍是"调试技巧"性质
  （[书源调试工具完全指南](https://blog.csdn.net/gitblog_00440/article/details/156017657)）。
- 社区出现 AI 辅助生成插件（阅读书源生成插件 v0.6.0）—— 生成靠 LLM，校验仍缺位。

### RSL 现状（【实测】代码）

- **LSP server 已交付**（`crates/rsl-lsp`，手写 stdio JSON-RPC）：publishDiagnostics（编译诊断
  + JSON key 定位）/ hover（变量来源契约/命名空间/步骤键）/ completion（18 命名空间 + 31 步骤键）/
  definition（var: → 声明处）；冒烟 5/5（`tools/lsp_smoke.py`）。
- JSON Schema 2020-12（29 `$defs`）可直接驱动表单。
- ROADMAP：可视化编辑器 ⬜ 未开始。

### 业界参考（【联网】）

- **LSP-for-DSL 先例**：Bünder et al. 2019 用 LSP 给 Entity-DSL 接入两个 IDE
  （[ACM](https://dl.acm.org/doi/10.1145/3339255.3339258)）——一次语言服务，多编辑器复用；
  LSP 本身是 JSON-RPC（[Wikipedia](https://en.wikipedia.org/wiki/Language_Server_Protocol)、
  [VS Code 扩展指南](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)）。
- **JSON 规则可视化双模式**：[JSONLogic Visual Editor](https://jsonlogiceditor.dev)（可视化构建器与
  JSON 文本双向同步）；[Microsoft RulesEngine](https://github.com/microsoft/RulesEngine)（JSON 规则引擎）；
  [SurveyJS 的 schema 驱动表单综述](https://surveyjs.io/stay-updated/blog/best-json-form-editor)
  ——**"可视化写 JSON、文本编辑时由 LSP 校验"的混合模式是成熟做法**。

### 差距与可选设计空间（不决策）

| 选项 | 形态 | 成本 |
|---|---|---|
| A. VS Code 扩展（先行） | 打包现有 LSP + JSON Schema + snippets + 调试命令 | 低（LSP 已 5/5），收益即时 |
| B. Schema 驱动表单编辑器 | SurveyJS 模式：JSON Schema → 表单 → 生成 `stages` 骨架 | 中；表单只覆盖结构化部分，选择器仍是文本 |
| C. 全可视化（点选生成） | per-stage 节点图 | 高；JSON↔UI 双向同步是难点 |
| D. 调试面板 | `rsl run --trace` 结构化输出（现 trace 已有）→ 可视化展示 | 中；与 A/B 可叠加 |

## 5. 源内远程依赖

### 阅读怎么做

- 【联网】`jsLib` 字段引入远程 JS 库（URL），多源共享加解密/解析函数；配合 `java.cacheFile`
  缓存（[Legado 规则说明](https://mgz0227.github.io/The-tutorial-of-Legado/Rule/source.html)、
  [legado-vox](https://github.com/Autsunset/legado-vox)）。
- 【官方·已裁决】RSL **明确不采纳**（`RSL-1.0.md` §16）：理由是"源必须自包含、可审计、可离线；
  远程脚本让'这份源做什么'不可判定"。

### 供应链视角（【联网】）

- 远程脚本库的现实风险与 npm 生态同构：typosquatting/slopsquatting 攻击在 2026 年仍活跃
  （[Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/05/28/typosquatted-npm-packages-used-steal-cloud-ci-cd-secrets)）；
  npm 无强制审核/签名/身份验证（[供应链攻防综述](https://learn.github.com/well-architected/library/application-security/recommendations/managing-dependency-threats)）；
  缓解共识 = **签名/attestation 校验 + 版本锁定 + 完整性哈希 + 私有镜像**。
- 迁到书源场景：`jsLib` 是"运行时任意 URL 拉代码"——比 npm 更糟（连 registry 审核都没有），
  且书源分发链（网盘/频道）无任何完整性保证。

### RSL 现状与可选设计空间（不决策）

| 选项 | 形态 | 与合规/审计立场的关系 |
|---|---|---|
| A. 维持不采纳（现状） | lib 必须内联自包含 | 立场最硬；共享代码靠 `rsl build` 时的人工组织 |
| B. **构建期内联**（受控远程） | `rsl build` 支持拉取远程 JS → 内联进源 → manifest 记 sha256 → 运行时零网络 | 把"远程依赖"变成"构建时依赖"：审计面恢复完整，同时解决多源复用诉求 |
| C. `x-` 扩展通道 | 宿主自定义 `x-jslib`（RSL 不背书） | 不进标准，生态自决 |
| D. 签名源包 | `rsl pack` 支持对整包签名 + 校验 | 与分发层"只发程序"原则正交，可作为后续独立议题 |

## 6. 失败语义

### 阅读怎么做

- 【源码】异常粒度停在"源级"：请求异常经 `getErrStrResponse` 包装、`loginCheckJs` 500 重抛
  （`WebBook.kt` 五阶段）；UI 呈现为"无结果/失败"，原因不可区分。**没有错误码体系**。
- 【联网】社区只能靠外部工具批量检测（[LS-Toolkit](https://github.com/aminaqvq/legado-source-toolkit)
  连通性检查/质量评分）+ 人工调试（[调试指南](https://blog.csdn.net/gitblog_00440/article/details/156017657)）。

### RSL 现状（【实测】代码）

- 31 错误码 + 5 警告码（36 全表），三分语义（合法空/可降级/失败），诊断十字段
  （code/severity/stage/path/rule/message/hint/sample/degraded/retryable/partial）。
- 属性测试 P3 锁死 severity↔code 全表；lint 20 条；批量聚合报告（batch_report 同构）。
- LSP 把诊断实时推送编辑器（path → JSON key 定位）。

### 业界参考（【联网】）

- **rustc 诊断设计**（[rustc dev guide](https://rustc-dev-guide.rust-lang.org/diagnostics.html)）：
  结构化诊断 = code + span + label + **machine-applicable suggestion** 分离；
  好消息是 rustc 错误消息口碑正是这种投入的回报。
- **错误消息三要素**（[What's in a Good Error Message?](https://quuxplusone.github.io/blog/2022/01/12/whats-in-a-good-error-message/)）：
  Context（在哪/为何）+ Error 本体 + **Mitigation（怎么修）**——RSL 的 `path/hint` 字段
  已对应前两者与 Mitigation 的雏形。
- **阶段分离**（[langdev 讨论](https://www.reddit.com/r/ProgrammingLanguages/comments/jtxbdj/soliciting_ideas_on_generating_good_compiler/)）：
  类型检查记录结构化错误、诊断阶段单独格式化——RSL 的 Diagnostic 结构已经是这个形态。
- UX 原则（[NN/g](https://www.nngroup.com/articles/error-message-guidelines/)）：
  可见、建设性、尊重用户投入——映射到宿主 UI 呈现层。

### 差距与可选设计空间（不决策）

| 选项 | 形态 | 说明 |
|---|---|---|
| A. code → 宿主文案映射表 | 规范层发布"每码的用户话术 + 建议动作"资源（i18n 键） | 宿主不必各自猜语义 |
| B. 机器可读修复建议 | Diagnostic 增加 `fix` 结构（suggestion 范围 + 替换文本），LSP 变成可应用的 code action | 对齐 rustc 的 machine-applicable suggestion |
| C. 批量连通性校验命令 | `rsl check <dir> --probe`（对标 LS-Toolkit：批量测活/评分） | import 已有聚合报告；补"运行期连通性"维度 |
| D. 诊断快照/回放 | trace + Diagnostic 快照成文件，可离线分享排查 | 建立在现有 trace 机制上 |

## 7. 汇总：差距 × 建议（仅供后续决策参考，未拍板）

| 项 | 差距等级 | 最经济的下一步 | 立场冲突点 |
|---|---|---|---|
| 登录 WebView | 中（端口在、协议缺） | `LoginSessionPort` 协议 + UA 一致性契约（吸收 Tachiyomi 教训） | "UI 不进标准" vs 交互登录本质是 UI |
| 自动重登 | 中低（与阅读同构） | 选项 B（宿主驱动）成本最低；A 需硬上限护栏 | 自动化 vs 可预测性 |
