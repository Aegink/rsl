## 2. 阅读侧证据：发现（explore）

来源：技能包知识库【源码】S1 ExploreRule.kt/ExploreKind.kt + KERNEL-COMPARE【源码】。

### 2.1 结构

- `exploreUrl`（入口定义，BookSource 字段）+ `ruleExplore`（解析规则，与 SearchRule 同构实现 `BookListRule`，10 字段：bookList/name/author/kind/intro/coverUrl/wordCount/lastChapter/updateTime/bookUrl）。
- `exploreUrl` 四种写法：
  1. `名称::URL`（换行/`&&` 分隔）；
  2. `\n` 分组标题；
  3. JSON 数组（带 FlexChildStyle 布局）；
  4. `@js:` 动态生成（聚合源做源初始化 + 返回分类）。
- **ExploreKind 5 种交互类型**（ExploreKind.kt 实证）：`url`（分类链接）/`text`（分组标题）/`button`/`toggle`/`select`（筛选器），字段含 title/url/action/chars/default/viewName/style。
- 聚合源范式：`select` 控件 + `infoMap["模式"]` 读当前选择 + `action:"java.refreshExplore()"` 重刷发现页 → 页面随模式动态变化。
- 分页：`{{page}}` 占位符；**exploreUrl 的 JS 里翻页必须写字面占位符**（分类初始化上下文无 `page` 绑定，活 JS 会崩——三上下文注入表，知识库实证）。
- 启用开关：`enabledExplore: true`；发现 `bookList` 空 → **整条回退 ruleSearch**（BookList.kt:86）。

### 2.2 与 RSL 的结构性对比（KERNEL-COMPARE §F.47 实证结论）

| 维度 | 阅读 | RSL |
|---|---|---|
| 发现结构 | 扁平 `List<ExploreKind>`，无树，分组靠 UI 约定 | **显式嵌套 `groups` 树**（有二级 groups 的项只作分组标题不请求） |
| 动态分类 | `@js:` 生成 | `groupsFrom`（选择器从站点抓分类 + map） |
| 筛选 | ExploreKind select/toggle（UI 控件语义） | `filters`（**数据选择声明**：key/label/options/default/persist；值走 `var:filter.<key>`） |
| 交互控件 | 引擎内建（发现页渲染控件） | **宿主 UI 约定**（filters 只是数据，控件由宿主渲染——"UI 不进标准"） |

**结论**：RSL 的 explore 契约是**更强**的（显式树 + 数据化筛选，KERNEL-COMPARE F.47 原文"发现结构 RSL 强"）。
阅读截图里的两级 tab（排行榜/男频分类… → 榜单/热搜榜…）在 RSL 里就是 `groups` 两级树；筛选器 UI 在 RSL 里就是 `filters` 的宿主渲染职责。
**差距不在契约与内核，而在"编辑器/调试器没有把它露出来"。**

## 3. 阅读侧证据：调试器

### 3.1 App 内调试页（用户截图对应物）

- 顶部：**阶段下拉**（搜索测试/书籍详情测试/章节列表测试/正文测试/发现测试）+ 关键词输入 + 页码 1-10 快切。
- 每阶段 **4 个 tab**：
  1. **原始数据**：响应原文（工具条：响应解析/取消换行/美化代码/还原代码/到底部）；
  2. **解析结果**：out 解析后的 JSON（美化工具条）；
  3. **协议标头**：原始地址（模板形态）、请求地址（编码后）、重定向、重试次数、请求引擎（http）、请求方式（GET）、请求类型（正式请求）、解析方式（jsonpath）等；
  4. **可视界面**：解析结果渲染成书卡片（封面/书名/作者/分类/字数/简介）——**"解析结果长什么样"的直接预览**。
- **链式传值**：搜索测试点击某本书 → 该书进入"书籍详情测试"（顶部显示封面/书名/作者/最新）；详情 → 目录 → 正文同理。发现的选中条目来自阅读书架（详情的输入是 App 里的书，不是发现页）——对应 RSL 契约 `var:book = 宿主显式传入的选中条目`（§6.4，天生一致）。

### 3.2 调试协议（自动化入口，legado-debug.py 实证【源码】）

- App 开启 Web 服务（HTTP 1122 + WebSocket 1123）：
  1. `POST` 保存书源 → App 立即拿到最新规则；
  2. WS 连 `/bookSourceDebug`（订阅源 `/rssSourceDebug`）；
  3. 发 `{tag: 源URL, key: 调试键}`；
  4. 收调试输出流直到连接关闭。
- **五阶段 key 约定**（phase 1=正文 2=目录 3=详情 4=搜索 5=发现）：
  - `关键字` = 搜索；`分类名::URL` = 发现；`URL` = 详情；`++URL` = 目录；`--URL` = 正文。
  - **前置阶段须先成功一次**（链式上下文依赖）。
- 这就是"修改规则实时生效"的机制：**保存即最新规则**（App 内存里没有旧规则缓存参与调试）。

### 3.3 官方 web 编辑器（【联网】gedoor/legado_web_source_editor）

- Vite + pnpm 前端，两个路由：`/bookSource`（书源编辑）+ `/rssSource`（订阅源编辑）。
- 调试 = **把 VITE_API 指到阅读 App 的 web 服务（IP:1122）**——执行永远在 App 内核，前端只是壳。
- 已迁移进主仓 `modules/web`。

### 3.4 生态衍生（【联网】）

- Legado Tauri 桌面版（开源阅读桌面化）；阅读 Sigma / Legado_Max 等衍生 App；
- 社区 Python 调试引擎（模拟 Kotlin 解析器）——其文档核心原则直说：**"模拟调试只是近似，官方源码才是唯一权威；模拟失败就让用户去真实 App 测试"**。

> **对 RSL 的关键启示**：阅读生态里"模拟内核 vs 真实内核"是常态分歧。RSL 内核是单一 Rust 实现（CLI/LSP/wasm/FFI 四端同源 bincode）——**调试器无论跑在哪，调同一内核 = 模拟与真实的分歧天然消失**。这是立意层面的结构性优势。

## 4. RSL 侧现状盘点

### 4.1 explore：契约与内核都在（【实测】）

- 契约：R§6.3——`filters`（数据选择声明：options/default/persist）、`groups` 显式树（二级只作分组标题）、`groupsFrom` 动态抓分类、深度合并进 request、`var:group` / `var:filter.<key>` 注入。
- 内核：`stages.explore` 合法阶段（analyze/mod.rs:286）；search/explore 至少其一（:295）；`RunInputs { group, filter }` 注入 `var:group`/`var:filter.<k>`（stage/mod.rs:335-340）；list 型契约 search/explore/toc 同构（:1493-1559）。
- **对照截图**：两级 tab = groups 两级树 ✓；筛选器 = filters（宿主渲染）✓；发现独立入口 = explore 是独立阶段 ✓；发现→详情 = 选中条目经 `var:book` 传入（§6.4 契约原生）✓。
- **编辑器侧零露出**：表单编辑器只建模了 search/detail/toc/content 的 request/out（form-model.js modeledPaths 无 explore）。

### 4.2 调试能力盘点（对照 2.1~2.5 逐条）

| 诉求 | RSL 现有 | 缺口 |
|---|---|---|
| 2.1 实时生效 | LSP didChange 全量诊断（静态）；`rsl run` 可重复执行 | 编辑→**自动重跑当前调试阶段**的管道不存在 |
| 2.2 五个调试页面 | `rsl run <src> <stage>` 五阶段都能跑（explore 含 group/filter 注入） | 无 UI；无阶段会话 |
| 2.3 链式传值 | `--book key=val` / `--chapter key=val` 手动注入；`var:book`/`var:chapter` 契约 | **自动编排**（上阶段结果选中条目 → 下阶段输入）不存在 |
| 2.4 四页面数据 | 内核 `HttpResponse{status,headers,body,final_url,ms}`（协议标头数据在）；`TraceEntry{matched,ms,bridge,sample}`；`--trace-json`（rsl-trace/1） | **原始响应体/请求详情不外吐**（run 只出 out）；无四页面 UI；无可视渲染 |
| 2.5 独立编辑器 | rsl CLI 九命令 + rsl-lsp + rsl-wasm + rsl-ffi | 无产品形态整合 |

### 4.3 内核为"调试器"需要的最小增量（候选，不拍板）

1. **调试执行产物结构**（rsl-trace 扩展或 rsl-debug/1）：单次 run 阶段执行 → `{ request: {url, method, headers(请求侧), redirect, retries, engine}, response: {status, headers, body_ref, ms}, out: 解析结果, trace, diagnostics }`——四页面数据面一次拿齐；body 大时用引用/截断。
2. **链式会话语义**：`detail/toc/content` 的输入=上阶段选中条目（`var:book`/`var:chapter` 契约已定，内核 run_stage 已支持注入——缺的是编排层约定，属工具层非语言层）。
3. **filters 交互**：宿主把 filters 选项渲染成控件 → 取值经 RunInputs.filter 注入——内核已支持，纯 UI 工作。

## 5. 业界参考（【联网】）

| 参考 | 可借鉴点 |
|---|---|
| **DAP（Debug Adapter Protocol）** | 三层架构：IDE ↔ Debug Adapter ↔ 运行时；"N+M 适配"避免 N×M 组合。RSL 若做调试协议，可与 LSP 同进程（同一 stdio JSON-RPC 通道上自定义请求），不必引入完整 DAP——DAP 的断点/单步语义对"声明式规则"不适用，**阶段执行+数据查看**才是匹配的调试粒度 |
| **Postman/Insomnia** | 四窗格范式（请求编辑 / 响应原文 / 响应头 / 渲染预览）与用户诉求的四页面同构；URL 模板变量面板=filters UI |
| **阅读官方 web 编辑器** | 前端只做壳、执行全在内核服务——"编辑器薄、内核厚"的先例 |
| **Legado Tauri 桌面版** | 独立 app 形态可行（Rust 壳 + web 前端）——RSL 若做独立编辑器，Tauri + rsl-core FFI/CLI 是同构路线 |
| **社区 Python 模拟调试引擎** | 反面教材：模拟内核与真实内核的分歧是书源生态最大痛点；RSL 单内核同源是结构性优势，调试器**必须复用内核**（杜绝"编辑器里重实现解析"） |

## 6. 编辑器形态 × 立意校验（选项对比，供任务书挑选）

| 选项 | 形态 | 调试执行位置 | 优势 | 劣势 | 立意校验 |
|---|---|---|---|---|---|
| **A. VS Code 扩展 + rsl 调试服务** | 现有扩展加"调试"面板（webview 四 tab），spawn `rsl` 子进程（JSON-RPC stdio，与 rsl-lsp 同形态）或并入 rsl-lsp 自定义请求 | **同一 Rust 内核**（子进程 CLI） | 增量最小（LSP/表单底座全在）；实时生效天然（didChange）；跨平台 | 依赖 VS Code；webview UI 要自绘 | ✅ 跨端一致（同一内核执行）；✅ 失败可区分（诊断体系直通）；✅ 规则是数据（调试输出也是 rsl-debug/1 数据）；✅ UI 不进标准（面板是宿主工具）；✅ 单一事实源 |
| **B. 扩展 + wasm 内嵌** | 扩展里跑 rsl-wasm | wasm | 无子进程 | **浏览器沙箱无直连网络（CORS）→ 真实站点调试不可行**；webview 能力受限 | ❌ 真实调试是核心诉求，wasm 网络受限否决（抓包型工具必须本地进程） |
| **C. 独立编辑器 app（Tauri/Electron）** | 完整产品：源管理 + 编辑 + 调试 + lint + pack | rsl-core FFI 或 CLI 子进程 | 不依附 VS Code；可分发给人非开发者；产品完整（对齐 2.5"独立做完整编辑器"） | 成本最高（打包/分发/更新）；UI 从零 | ✅ 立意同 A；⏳ 成本分期（可作 P2，先 A 后 C 复用调试协议） |
| **D. rsl serve + web 前端** | CLI 内置 HTTP 服务（同阅读 1122 模式），任意 web 前端连 | CLI 内核 | 形态开放（多前端）；局域网协作 | 需要服务生命周期管理；安全面（本机端口）；S§17 边界（服务不落内容） | ✅ 同 A 的内核一致；⏳ 服务模式引入攻击面，需限本机回环 |

**倾向（供拍板）**：**A 立刻做（P1）**——五页面调试器进现有 VS Code 扩展，调试执行=本机 rsl 子进程（同一内核），实时生效用 didChange 防抖重跑；**C 作为 P2 演进**——A 的调试协议（rsl-debug/1）原样搬到独立 app，不返工。B 否决；D 可与 A 并存（后续可选）。

### 立意公理逐条校验（A 方案）

| 公理 | 校验 |
|---|---|
| 跨端一致 | 调试执行 = 用户机上的同一 rsl 内核；调试结果即内核结果（不存在"编辑器解析"平行实现——阅读生态反面教训的正面解法） |
| 失败可区分 | 四页面里诊断体系直通（rsl-debug 产物带 diagnostics 全结构） |
| 能力按需付费 | 调试 webview/登录型阶段 → 无宿主能力即 E_UNSUPPORTED 原样展示（诚实暴露限制，不假装成功） |
| 规则是数据 | 调试产物定义 `rsl-debug/1` schema（同 trace.schema.json 先例，H 稳定性承诺） |
| 源自包含可审计 | 调试是本机工具行为（浏览器同性质）；响应体仅内存预览不落盘不进报告（S§17 边界延续） |
| UI 不进标准 | 调试面板是宿主工具；协议（rsl-debug/1）进 schema，UI 不进 |
