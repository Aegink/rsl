# CONCEPTS · RSL 心智模型

> 只讲"为什么这么设计"。字段细节查 `REFERENCE.md`，任务配方查 `PATTERNS.md`，契约本身查 `RSL-1.0.md`。
> 版本 **2.0**。文中 `§x.y` 一律指 `spec/RSL-1.0.md` 的章节号。

第一次读 RSL 的人，困惑通常不在语法，而在"为什么不照 Legado 那样写"。下面 10 节，每节对应一个被反复踩过的设计决定：先给结论，再给代价。

| # | 主题 | 一句话结论 |
|---|---|---|
| 1 | 规则是数据 | 每个"魔法后缀"都是一个可以编译期检查的字段 |
| 2 | 一源一站 | 聚合是宿主职责，不是源的能力 |
| 3 | 阶段契约 | 阶段之间只有 `out`，注入必须显式 |
| 4 | 命名空间 | 选择器没有"默认解释"，因为没有默认才不会猜错 |
| 5 | 六层状态 | 状态放错层是绝大多数源 bug 的根因 |
| 6 | 逐章成本 | 19 秒超时被消灭在编译期，不是靠经验 |
| 7 | 四种结果 | 空、降级、失败是三种东西，三种错误码 |
| 8 | 两档脚本 | 纯函数与受控上下文，中间没有"逃生舱" |
| 9 | 能力声明 | 缺能力要能点名，且只禁用该入口 |
| 10 | 多源合并 | 同一个站点在三个 App 里必须给出同一种合并结果 |

## 1. 规则是数据，不是代码

Legado 把一条规则写成**一个字符串**：`##正则##替换`、`[!2][0:10]`、`URL,{"method":"POST"}`、`@@css:…`。字符串内部的每一段都有独立语义，但类型系统看不见它们，所以拼写错误只能等到运行时、等到用户点下去、等到三周后的"目录加载失败"。

RSL 的做法是把同一件事拆成**字段**：`transform.regex.all` 是布尔、`range` 是切片声明、`request` 是对象、`attr` 是取值方式。这不是为了好看，而是为了让编译器有东西可查——`E_SCHEMA`、`E_REF`、`E_TYPE`、`E_COST` 全都建立在"字段可见"这个前提上（§11.1）。

代价要说清楚：**写起来比一行字符串长**。一个"取书名并去空格"在 Legado 里写成 `css:.title@text##\s+##`，在 RSL 里是三个字段。收益是这条规则可以被 `rsl lint` 不联网检查（§13.3 的 20 条），可以被 `rsl build` 逐字节复现，可以在 code review 里被 diff 出来。

```jsonc
"wordCount": {
  "$": "css:span.words",                        // 取值：显式命名空间
  "transform": [{ "number": { "unit": true } }],// "12.3万字" → 123000
  "optional": true                              // 缺失不报错，不静默变空串
}
```

判据很简单：**如果一条规则只能靠"读引擎源码"才知道它做什么，它就是代码而不是数据。**

## 2. 一个源 = 一个站点

一条 RSL 文档描述的是**一个站点**。站点改版，坏一个文件；站点下线，删一个文件。这条约束在 §16 里写成硬规则："单源内聚合多站点"永远不合法。

反过来推：为什么聚合必须归宿主？因为折叠需要**看见全部候选**。源 A 只能拿到源 A 的结果，它无法知道源 B 也返回了《同一本书》，因此源内聚合的"去重"注定是局部去重，全局重复照样出现在 UI 里。宿主同时跑 N 个源，才能按 §12.4 的 `merge` 契约做跨桶比较。

代价：用户要装 N 个文件而不是 1 个。收益：源的失败半径被限制住——一个源的 `E_NO_MATCH` 不会污染另一个源的结果，宿主并行跑、逐个收敛，慢源不会拖死全部（§12.2 不设整体搜索超时）。

```jsonc
// a.example 的书源：只认识 a.example 的 DOM
{ "rsl": "2.0", "id": "a.example", "baseUrl": "https://a.example", "stages": { /* A 的选择器 */ } }
// b.example 的书源：另一个文件，另一套选择器
{ "rsl": "2.0", "id": "b.example", "baseUrl": "https://b.example", "stages": { /* B 的选择器 */ } }
// 宿主把它们放进同一个搜索框 —— 这就是聚合
```

Legado 生态里"一个源写 8 个站点"很常见，结果是任何一个小站改版都要动整个文件，且没人敢删已经死掉的分支。

## 3. 阶段契约：`out` 是唯一出口

阶段固定五个：`search` `explore` `detail` `toc` `content`（§6）。宿主另有需求的书架、历史、评论走 `hostStages`，但那不新增语法。每个阶段的唯一输出是 `out`，字段含义由契约规定，引擎对这些保留字段的行为是**强制**的，不是约定。

最容易被质疑的一条：**不存在"第一个搜索结果自动变成 `var:book`"**（§5.4）。`detail` 的 `var:book` 必须是宿主显式传入的选中条目，其字段来自 `search`/`explore` 的 `out.map` 声明；`content` 的 `var:chapter` 同理来自 `toc.out.map`。这条硬约束换来的是：`var:book.tocUrl` 拼错在编译期就是 `E_REF`，而不是运行时拿到 `undefined` 然后请求 `https://site/undefined`。

代价：源不能再依赖"引擎帮我兜一下"。收益：阶段之间没有共享可变全局，上下文可快照、可重放（§12.1），每个阶段都能单独跑、单独录 fixture、单独断言。

```jsonc
"search": { "out": { "list": "css:li", "map": {
  "name": "css:a",                                  // → 条目字段 name
  "url":  { "$": "css:a", "attr": "href" }          // → 条目字段 url
} } },
"detail": { "request": { "url": "var:book.url" } }  // 宿主传进来的条目，不是"第一个结果"
```

## 4. 选择器是显式命名空间

`§3.2` 一共 18 个命名空间：`css:` `xpath:` `json:` `re:` `text` `owntext` `html` `tag` `attr:` `const:` `var:` `let:` `session:` `token:` `cookie:` `cache:` `lib:` `expr:`。**不存在"无前缀默认解释"**——这是 RSL 相对 Legado 最重要的一处改动。

Legado 要做 8 级前缀猜测：`/` 开头当 XPath、`$.` 开头当 JSONPath、`@@` 去掉前缀、`@` 取属性……问题是 `/` 既可能是路径也可能是正则字面量的一部分，`##` 一出现整条链的语义就整体切换。猜测需要上下文，而上下文在字符串里没有位置。命名空间把这个判断挪到**加载那一刻**：编译器看见前缀就知道语义，看见没有前缀就报 `E_SELECTOR`。

代价：每个选择器多打 3~5 个字符。收益：语义在加载期确定，`re:` 被限定在 RE2 子集以保证 Rust/Swift/JS/Kotlin 行为一致（§3.4），不支持的写法（反向引用、前后向断言）在编译期就是 `E_REGEX_UNSUPPORTED`，而不是"Android 能跑、WASM 崩溃"。

另一个结构性好处：一个选择器对象把**取什么**（`$`）和**怎么变换**（`transform` 管道）分开，所以"先取 HTML、反转义、再当 JSON 解析"能显式写出来（`parse`，§6.1.2），而不是靠一串后缀去猜执行顺序。

```jsonc
"css:div#list > li"       // HTML 节点
"json:$.data.books[*]"    // JSON 值
"re:第(\\d+)章\\s*(.+)"   // 字符串
"attr:href"               // 属性
"var:book.tocUrl"         // 上下文变量
```

## 5. 六层状态

§5.1 把状态层写死成六层。真实源里绝大多数"莫名其妙的 bug"都不是规则写错，而是**状态放错层**：把本次运行的临时值写进持久配置（于是"重启后开关失效"或"这个设置跟着书传播"），把派生结果当成用户设置（于是缓存过期后设置被覆盖）。

| 层 | 命名空间 | 生命周期 | 可写者 |
|---|---|---|---|
| 源配置 | `var:` | 跟随源，用户可编辑 | 用户 / `script` |
| 登录令牌 | `token:` | 跟随登录态 | `login` |
| 会话 | `session:` | 单次运行 | `script` / `let` |
| 缓存 | `cache:` | 按 TTL | `script` / `cache` 块 |
| 阶段内 | `let:` | 单个阶段 | 阶段 `let` |
| 上下文 | `var:` | 宿主注入 | 宿主 / 契约 |

三条判据：用户设置只写源配置层；派生结果只进缓存层；会话层不得冒充持久配置。加两条硬约束：`vars.<k>.secret: true` 的值永不进入日志、导出、错误信息与 `--trace`（§5.2）；登录态隔离键是"源 id + 域名 + 登录名"，所以换账号天然隔离、同名新源不继承旧 Cookie（§4.5.3）。

代价：源作者要判断"这个值属于哪层"。收益：任何状态都有明确的生命周期，缓存键必须带维度（`book.id` / `mode` / 源身份），否则会串书（§12.3）。

```jsonc
"vars": { "line": { "value": "https://line1", "persist": true } }  // 用户可改，跟源走
"token:auth"        // 登录产出，跟登录态走
"session:nonce"     // 单次运行
"cache:richToc"     // 按 TTL，可失效
"let:ts"            // 单阶段，出阶段即丢
"var:book.url"      // 宿主注入，只读
```

## 6. 逐章成本 `E_COST`

`toc.out.map.*` 是**逐章求值**的，成本随章数线性放大：

```
阶段耗时 ≈ 项数 × 逐字段规则数 × 每条规则的跨桥次数 × 单次跨桥成本
```

实测数据：807 章 × 3 字段 ≈ 4800 次跨桥 ≈ **19 秒**，直接撞穿宿主预算，用户看到的只是一句"目录加载失败"。这不是理论风险，是这类引擎最常见的线上故障。

所以 RSL 把它做成**加载期错误**而不是性能建议（§6.5.1）：逐章规则只允许白名单内的选择器与管道步骤，出现 `script`、`lib.ctx`、`cache`、`http`、`expr:now()`、`expr:rand()`、`cookie:`、`token:` 一律 `E_COST`，并给出"把该字段的计算挪到 `list` 选择器的父规则里一次算完"的提示。

代价：有些写法变啰嗦——想算签名就不能在逐章规则里当场算。收益：19 秒超时在编译期消失，而不是在三端各自的 profile 里各查一遍。这也是"凡是被证明有用的工程优化必须进标准"（§0.2 第 6 条）最直接的一次落地：真实站点普遍需要"详情页与目录页同页就不重复请求"，所以 `toc.reuseDetailHtml` 是标准的一部分（§6.5.2），不该让每个作者自己想办法。

```jsonc
"toc": { "out": { "list": "css:#list li", "map": {
  "title": "css:a",        // 合法：逐章规则里的纯选择器
  "words": "css:.wc",      // 合法
  "vip":   "css:i.vip"     // 合法
} } }
// 改成 script / cookie: / expr:now() / 在 map 里发请求 → E_COST，编译期拒绝
```

## 7. 四种结果

Legado 把所有异常压成空串，于是宿主无法区分"这本确实没有""接口返回了错误页""登录过期了"。RSL 强制分成四种（§11.3）：

| 情况 | 表现 | 宿主该做什么 |
|---|---|---|
| 成功 | 必需字段齐、业务状态正确 | 正常渲染 |
| 合法空 | `emptyOk: true` → `[]`，**不报错** | 显示空态，不弹错误 |
| 可降级 | 增强字段失败 → 主结果保留 + `degraded: true` + `W_DEGRADED` | 保留主结果，隐藏或弱化增强入口 |
| 失败 | 对应错误码 | 按码决定重试 / 登录 / 报错 |

配套两条：`emptyOk: false`（默认）时列表为空是 `E_EMPTY` 而非 `error`；`verify` 用来识别"HTTP 200 但返回了错误页/别的内容"，失败是 `E_VERIFY`。降级的方向是单向的——**增强失败不得清除已取得的核心结果**：富目录失败要保留普通目录，推荐为空要隐藏入口，歌词失败要保留音频，弹幕失败返回空轨道。

所有错误都是结构化对象（`code` / `severity` / `stage` / `path` / `rule` / `message` / `hint` / `sample` / `degraded` / `retryable`，§11），并且绝不返回裸空串。

这条区分不是为了好看。宿主 UI 要据此决定"显示空态 / 隐藏入口 / 弹重试 / 弹登录"，没有这个区分，界面就只能靠猜：把登录过期渲染成"没有结果"，用户会以为站点没有这本书。

```jsonc
"out": {
  "emptyOk": true,                       // 合法空：[] 而不是错误
  "verify": { "contains": "var:kw" },    // 结果必须含关键词，否则 E_VERIFY
  "list": "json:$.data[*]",
  "map": { "name": "json:$.title" }
}
// 增强字段失败 → 主结果保留 + W_DEGRADED
```

## 8. 两档脚本

`lib` 只有两档（§7.1），中间没有第三档：

| 档 | 能做什么 | 调用位置 |
|---|---|---|
| `pure` | 纯计算：字符串、数组、正则、JSON、数学 | `transform.js`、`lib:fn` 选择器、`let` |
| `ctx` | 读写会话与上下文、发请求、读缓存、读源配置 | `script.*`、`transform.js`（`ctx: true`） |

为什么不是一档？真实源 90% 的逻辑——签名、解密、归一化、读配置——**既不是纯函数也不是阶段钩子**。只给纯函数，作者会把一切都塞进 `after`，结果比 Legado 更难维护；把 IO 全放开，就回到"脚本逃生舱"。两档的分界线是"有没有副作用"，正好对应编译期能不能做成本分析：`pure` 可以进逐章规则，`ctx` 一旦进逐章规则就是 `E_COST`。

三个钩子的作用对象必须明确（§7.5）：`before` 改请求、`onResponse` 改**原始响应**、`after` 改已解析的 `out`。`onResponse` 是 v2.0 新增——它对应 Legado 里名字与作用不符的 `loginCheckJs` / `bodyJs`，专门解决"响应必须在解析之前被改写"这类此前只能靠猜的需求。

明确不提供的清单同样重要：`java.*`、`org.*`、`globalThis.fetch`、`require`、`process`、文件系统、任意反射、`eval`（§7.2）。`ctx` 只给受控接口：`ctx.http`、`ctx.session`、`ctx.cache`、`ctx.cookie`、`ctx.config`、`ctx.crypto`、`ctx.log`。

```jsonc
"lib": {
  "pure": "function clean(s){ return s.replace(/[《》]/g,'').trim() }",  // 无 IO
  "ctx":  "function sign(ctx, s){ return md5(ctx.config('salt') + s) }" // 受控 ctx
},
"stages": { "search": { "transform": [{ "js": "lib:clean" }] } }  // pure 可进任何地方
// "js": {"fn":"lib:sign","ctx":true} 只能在阶段钩子；放进逐章规则 → E_COST
```

## 9. 能力声明与降级

`requires.features` 声明的是"我用了什么"，不是"请给我什么"（§9.1）。引擎缺对应能力 → `E_UNSUPPORTED`，错误信息必须**点名缺哪个 feature 或哪个算法**。`crypto` 更进一步按算法声明：`["aes-cbc", "hmac-sha256", "md5"]`，而不是笼统的"我要加密"。

| feature | 含义 |
|---|---|
| `js` | 有 JS 沙箱（`lib` / `script`） |
| `time` / `random` | `now()` / `rand()` |
| `crypto` | 加密原语，具体算法在 `crypto` 数组里按名声明 |
| `font` | 字体解析与字形映射 |
| `webview` | WebView 取数与嗅探 |
| `detect` | 编码自动探测 |
| `xpath` / `jsonpath` / `css` | 对应选择器后端 |

为什么按 feature 而不是按平台：iOS 有 WebView、Android 有、WASM 没有；源不该知道这件事，也不该为它写分支。渲染降级链同理——`http`（默认）→ `webview` → `auto`（先 HTTP，命中 `autoUpgradeIf` 再升级一次），不要为了少数站点让所有请求都付渲染成本（§9.3）。

`hostStages` 是同一个思路的延伸：宿主声明自己支持哪些扩展阶段，源声明了宿主不支持的阶段时只禁用该入口，**不影响五阶段**（§6.8）。代价：多写一行 `features`。收益：能力缺口变成一句能读懂的报错，而不是一个白屏。

```jsonc
"requires": {
  "engine": ">=2.0 <3.0",
  "features": ["js", "crypto", "webview"],
  "crypto": ["md5", "aes-cbc"]
}
// 引擎缺 webview → E_UNSUPPORTED，报错点名 "webview"，只禁用该阶段
```

## 10. 多源合并是契约

搜索是多源并行的，"同一本书被 5 个源都返回"是常态。Legado 用 4 个桶 + `origins.size` 处理，问题是**跨桶不比较**：同一本书命中了 `exact` 桶和 `contains` 桶，就会重复出现两条。用户看到的不是"两个来源"而是"两个结果"。

RSL 把这件事写成契约（§12.4）：`merge.key` 定义折叠键（默认 `[name, author]`），`normalize` 先做归一化（`trim` / `t2s` / `lower` / `stripPunct`）——繁简与空格是最大的假重复来源；然后按 `exact` → `contains` → 其余 分档，同档内 `key` 相等的合并为一条，`origins` 累加、`weight` 取最大值；`crossBucket: true`（默认）时**不同档之间也要比较**。排序先按档位，同档内按命中源数降序、再按权重降序。

为什么必须有统一契约：这是宿主职责，但语义必须一致，否则三端各写一套，同一份源在三个 App 里给出三种结果——这正好违反第 4 条公理"跨端一致优先于方便"。宿主可以**忽略** `merge` 块用自己的策略，但一旦声明就必须按此语义执行，`rsl test` 的合并断言以契约默认值为准。

```jsonc
"merge": {
  "key": ["name", "author"],     // 折叠键
  "normalize": ["trim", "t2s"],  // 折叠前归一化：繁简/空格不得造成假重复
  "crossBucket": true,           // 跨档也强制比较（Legado 缺这一条）
  "order": ["exact", "contains", "weight", "sources"]
}
// 输出条目带 origins: ["a.example", "b.example"] 与 sources: 2
```

## 收尾：如果你只记三件事

1. **规则是数据。** 每一个"魔法后缀"在 RSL 里都是字段，所以它能在加载期被检查、被 diff、被断言。看到字符串里藏语义的写法，就说明设计退化了。
2. **没有隐式通道。** 阶段之间只有 `out`；`var:book` 必须由宿主显式传入、由上游 `out.map` 显式声明。所有"引擎帮我猜一下"的便利，最终都会变成 `https://site/undefined`。
3. **失败必须可区分。** 空、降级、失败是三件不同的事，三种错误码。任何"静默返回空串"的实现都等于把判断成本转嫁给宿主 UI。

这三条之外的一切——选择器命名空间、六层状态、`E_COST`、两档脚本、`requires`、`merge`——都是这三条在不同位置上的展开。

```jsonc
// 拿到一个源文件，先看这三处，就知道它靠不靠得住
"stages":   { "search": { "out": { "list": "css:li", "map": { "name": "css:a" } } } }  // 有没有 out 契约
"requires": { "features": ["js", "crypto"] }                                          // 能力有没有漫天要
"limits":   { "timeoutMs": 20000, "maxPages": { "value": 50, "on": "truncate" } }      // 有没有预算
```
